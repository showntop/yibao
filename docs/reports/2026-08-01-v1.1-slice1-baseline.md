### 8.3 失败归因（stage1 / stage2）

归因方法：预测点与 marks 中心逐一比对（预测点恰为某 mark 中心 ⇒ stage1 选了该数字；否则 ⇒ zoom 精化点）；无预测场景用 `scripts/debug_som.py` 取证模型原始回答（轮 1 两场景用默认模型；轮 2 vscode_statusbar 用 `YIBAO_VISION_MODEL=glm-4.6v-flash` 复现）。

- **stage1 选错号：17/24 场景次**（轮 1 8、轮 2 9）。典型：sysset_wifi 选 Wi-Fi 上一行 #4 而非 #5（41px，行级歧义，Slice 2A 起四轮复现）；vscode_explorer/vscode_tab 选窗口红绿灯 #1；轮 1 calc_eq 选 #16(+) 而非 #19(=)（同列相邻 46px）；safari_tab_close 两轮均选 #13 而非 #16。
- **stage1 字母回答解析失败：2 场景次（均轮 1）**。debug 取证：canvas_excalidraw_rect 模型答 `E（或F，根据区域划分，此处以E为例）`——带解释文字，`_parse_marked_action` 只认裸字母/JSON，丢弃（且 E 本身亦非正确区域 B）；vscode_statusbar 答 `<|begin_of_box|>F<|end_of_box|>`——特殊 token 包装，同样解析失败（F 亦非正确区域 D）。
- **stage1 选错字母：1 场景次（轮 2 debug 复现）**。4.6v debug vscode_statusbar：答 `\nA` → 解析成功 zoom A → `zoom_ground` 落空返回 None（正确区域为 D；区域选错则裁切内本无目标，精化必然失败）。轮 2 正考该场景无预测，与此机制一致（选错字母或格式失败，均属 stage1）。
- **stage2 偏了：0 场景次**。`zoom_ground` 在 24 场景次正考中零有效执行——**分层设计从未被真正检验到 stage2**：轮 1 模型 12 场景全部选数字（10 成功解析 + 2 字母格式失败），轮 2 同样全部以数字作答（11 成功 + 1 无预测；唯一一次字母选择出现在 debug 复现且选错区域）。

### 8.4 模型建议

两轮 SoM 同为 2/12（4.1v 中 calc_clear/calc_plus；4.6v 中 calc_clear/calc_eq），无模型间优劣差异；4.6v 免费端点 1305 拥塞严重（两次裸跑首调用即崩，wrapper 11 次退避约 8 分钟才跑通），其 baseline 路径亦 11/12 无预测。**无依据更换默认模型，维持 `glm-4.1v-thinking-flashx`；更换默认模型属 prod 配置变更，留作用户决策。**

### 8.5 遗留问题（供下一轮讨论，未擅自扩 scope）

1. **stage1 提示失效是当前首要瓶颈**：双轨 prompt 要求「目标不在红框元素上时输出字母区域」，但两模型 24 场景次 0 次选出正确字母——zoom stage2 无法触发，分层方案的核心收益未经验证。方向：prompt 强化 / few-shot / 结构化输出约束，需用户裁定。
2. **解析器对字母回答过严**（`_parse_marked_action` 只认裸字母 fullmatch 或 JSON）：模型带解释文字或特殊 token 包装的字母回答被丢弃（轮 1 两场景实证）。容错解析（剥离包装、搜首个独立字母）是低风险修复方向，属代码变更，本次评测 scope 内未动。
3. **行级歧义四轮复现**（sysset_wifi #4/#5，行框高 28px、标签 12px）：SoM 粒度问题长尾，单靠 prompt 难解。
4. **评测基建观察**：`_vision_create_with_retry` 不重试 429，端点拥塞时整轮报废；本次以仓外内联 wrapper 应对（429 属基建错误非模型回答，重试不改变评测语义），生产代码未改。

全路径对照（4.1v）：baseline 全屏 0-1/12、SoM 单发 2/12→0/12、SoM 双轨 2/12、**win 4/12（最佳）**。可及桶 4/7、盲桶 0/5，仍不达 spec §3 原线。

### 9.2 拒答归因（debug_win 取证）

- canvas/vscode_tab：thinking 模式下模型对冲答 `finish`（空 box 或 999 占位）——把感知题当推理题拒答。
- safari_nav_link：模型给出可用坐标但 **box 嵌套 `[[x1,y1,x2,y2]]`**，`_parse_action` 丢弃——解析器脆弱点，低成本可修。
- sysset_general：窗口右侧被终端遮挡污染（采集叠放），模型所见非纯设置面板。

### 9.3 结论

1. **「裁小图+原生 grounding」方向成立**：唯一拿到单项满分（calc 3/3）的路径，与生产 `prefers_raw_bbox` 设计直觉互证；zoom_ground 即该路径核心件。
2. **flash 级模型上限同样成立**：网页/canvas 内容基本不接地（拒答或错地），换协议救不了，需更强模型或接受现实水平。
3. **默认模型维持 `glm-4.1v-thinking-flashx`**（4.6v 全路径无优势且端点拥塞严重）。
4. 低成本可抬点（下轮候选）：`_parse_action` 解嵌套、grounding 场景 thinking 开关、拒答 prompt 强化——预估 win 可到 6-7/12，盲桶仍难。
