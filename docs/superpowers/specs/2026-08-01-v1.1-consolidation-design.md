# v1.1 收口夯实迭代设计（验收闭环 / 遗留补完 / 信任仪表 / 仓库卫生）

日期：2026-08-01  关联：`2026-07-30-click-grounding-som-design.md`、`2026-07-31-tts-provider-design.md`、`2026-07-31-watch-mode-hardening-design.md`、`2026-07-29-home-feed-design.md`

## 1. 目标

两周快速迭代（v1 底座 → v2 插件化 → OS 感 → 感知记忆 → watch → UI 重塑）之后，本迭代不写新能力方向，把已铺开的摊子收口夯实：

1. **验收闭环**：SoM 点击、watch 主动行为、TTS 三引擎——代码都齐了但都没有达标判定记录，用定量评测补上。
2. **遗留功能补完**：watch_command 跨重启恢复、深色模式、截图唤起——文档承诺过的三个 ❌ 项。
3. **信任仪表化**：主动行为（watch/提醒/后台事件）已有 Feed 记账，补上统计读模型与误报反馈回路，兑现「bounded, reviewable, reversible」。
4. **仓库卫生**：README 与代码对齐、eval_scenarios 填充、已合并分支清理。

**完成定义**：三套定量评测全绿 + 三个遗留功能落地并验收 + 信任仪表上线 + 文档/README/分支对齐，验收记录回写各对应 spec。

**排序原则**：方案 A 三段闸门——先造尺子（度量基座），再量基线（红绿报告），然后修与补，最后复测收官。每一步有据可依，验收不走过场。

**实施计划粒度**：本 spec 是迭代级设计，实施计划按 Slice 拆——Slice 0 一份计划先行，Slice 1 是纯跑评 + 写报告（不单独出计划），Slice 2 待基线红项明确后再出计划，Slice 3 随 Slice 2 计划附带。

## 3. 定量达标线（本迭代的验收契约）

| 能力 | 指标 | 达标线 |
|---|---|---|
| 点击（a11y 可及场景，click_control AX 直达） | 命中率 | 100%（硬线） |
| 点击（win 裁窗视觉兜底） | 命中率 | ≥4/12 且 calc 3/3（防回归线，2026-08-01 基线） |
| watch 触发（久坐/白名单/静默时段/后台命令） | 触发正确率 | 该触发 100% 触发，误触发 0 |
| TTS（edge / CosyVoice2 本地 / dashscope 云） | 合成成功率 | 3 句 × 3 引擎 100% |
| TTS | 起音延迟 | edge <2.0s，云 <1.5s，本地 <3s |
| TTS 本地引擎 | 峰值内存 | <2GB（arm64 spike 风险项） |
| watch_command 跨重启恢复 | 恢复率 | 脚本化重启 3 次，100% 恢复或明确标记失败 |

点击口径 2026-08-01 修订（三轮修复+复测证据见基线报告 §5-§9）：原线「可及区 100%（含 Safari 链接）/盲区 SoM ≥80% 且中位距 ≤20px」在 flash 级视觉模型上被证明不可达（协议三轮迭代 + 两模型对照），改为分档承诺——AX 直达场景保 100% 硬线；win 裁窗视觉兜底按实测基线防回归；盲桶（Canvas/Electron/网页内容）硬线废除，精度提升（parse 解嵌套/thinking 开关/prompt 强化/更大模型）转 backlog。watch 项都是确定性逻辑，不设中间态；TTS 延迟在网络正常情况下计量，异常记录在报告里注明。

## 4. Slice 0：造尺子（度量基座，不写产品功能）

1. **点击场景采集**：`eval_click.py --capture` 采满 ~12 场景——计算器/系统设置（a11y 易）、Safari 链接（中）、Canvas 自绘/Electron（盲），手填 GT；落入 `sidecar/scripts/eval_scenarios/`（根目录空壳 `scripts/eval_scenarios/` 移除或指向真实位置）。
2. **watch 触发评测**：脚本化驱动 watch tick 逻辑，断言两侧——久坐到点触发且静默时段不触发；白名单 app 触发截图建议且非白名单不触发；后台命令完成必报告。直接写成 pytest 用例（随现有 678 测试一起跑），不做手动脚本。
3. **TTS 验收脚本**：固定 3 句 × 3 引擎，记录成功率、起音延迟、（本地）峰值内存；手动跑，输出 JSON/表格。
4. **信任统计读模型**：纯 SQL 聚合现有 feed 表——主动行为按 kind/天的数量、已读率、ignored 率。不建新表；sidecar 暴露 `feed_stats` 查询命令，展示面挂在设置页「主动协助」分区的一个统计块（那里已是主动行为的控制面）。

## 5. Slice 1：量基线（出红绿报告）

跑三套评测，与第 3 节达标线对照，出红绿报告回写 `docs/`。红色项即 Slice 2 的修复清单——**Slice 2 的一半工作量由本步暴露，不预设**。

## 6. Slice 2：修与补

1. **红色项修复**：基线暴露什么修什么，修完单项复测转绿。
2. **watch_command 跨重启恢复**：任务落 SQLite，启动时扫描未完成任务恢复执行；恢复不了的明确标记失败进 Feed。脚本化重启 3 次验证。
3. **深色模式**：tokens.css 语义层补 dark 变体 + 组件硬编码颜色审计清零；人工目验三页（Home/插件/设置）。
4. **截图唤起**：全局唤起时抓屏随上下文进 run（`feat/global-invoke` 时代承诺的 ❌ 项）。
5. **误报反馈回路**：Feed 主动行为条目加 👍/👎；👎 写入 meta 并触发同类行为降频/静默规则（信任仪表的写侧，规则保持简单确定性，不引入模型判断）。

## 8. 测试策略

- 沿用现有惯例：eval 脚本（点击/TTS）手动跑、非 CI；watch 触发/恢复/反馈回路进 pytest（现有 678 测试体系内增加）。
- 前端深色模式：组件审计 + 人工目验，不加自动化截图对比（YAGNI）。
- 每个 Slice 完成以对应验证命令输出为准，不接受「应该好了」。

## 9. 非目标

- 感知 roadmap 纵深（B 源入库/晨间反刍/记忆巩固 job）——下一轮。
- `use_plugin` 按需暴露、场景插件、技能自积累——下一轮。
- 签名公证与分发——本轮不碰。
- 真实日用的打扰度数据统计——产品日用后再做，本轮只把仪表结构建好。
