## 1. 断点分析：为什么现在的视频创作体验是碎的

调研（2025-2026 产品实测与用户抱怨）收敛出三个行业级断点，本产品的机会就在断点上：

| 断点 | 现状 | 证据 |
|---|---|---|
| **局部修改** | prompt 改一处 = 整片重生成，烧 credit 且不可预测 | InVideo 实测（Motion The Agency） |
| **agent 不理解工程** | 剪辑 agent 覆盖用户已做的自定义编辑；只能做一键按钮能做的事 | Descript Underlord 官方论坛（Canny） |
| **资产与上下文搬运** | 脚本/图/视频/音频在 5+ 工具间人肉流转，上下文全丢 | InfoQ AI 漫剧工具链调查 |

对应到我们自己的工作台，断点的根因正是总纲诊断的三层墙：UI 属主在插件（编辑器不可复用）、跨插件调用被前缀锁死（资产搬不动）、agent 够不到表面层（不理解工程）。视频创作 case 的价值：**逼这三堵墙一起倒**。

反面教材的教训也记在这：

- **Descript 教训**：对话式剪辑的 agent 必须尊重并保留用户的自定义编辑，能做 UI 之外的链式批量操作，否则没有增量价值——"用户要的不是帮我点按钮，是理解我的工程文件并在此基础上工作"。
- **Capsule 教训**：基础精修能力缺了（调色、自由拖放）会被骂半成品。
- **剪映文字成片教训**：对话止步于"生成前"，生成后的调整入口仍是传统时间线——对话要贯穿全流程，不是只在开头接需求。

## 2. 调研综合：行业工作流与硬约束

### 2.1 标准流程的骨架（传统影视提供的结构）

```
立意 → 剧本 → 分镜 → 资产筹备 → 出镜头 → 粗剪 → 精剪 → 交付
```

四个**阶段门**（gate），每门一次显式人审：剧本锁定 → 分镜批准 → 画面锁定 → 交付。这正好落进我们的裁决器语义：阶段门 = 人按印，门内的事 agent 放手干。

### 2.2 AI 生成时代的硬约束（必须在设计里内置，不是后补）

- **抽卡是经济问题**：单镜头生成 45–300 元，项目级成功率实测 30–60%（官方口径 90%+ 不可信）。含义：多变体并排比较、废片回收站可对比、失败 prompt 记录复盘、**生成操作要配额确认**。
- **台词决定时长**：2.5–3 词/秒，分镜阶段就要做时长校验，别等生成后返工。
- **单镜头 3–8 秒、运镜限定几种**：生成模型的物理约束，agent 在分镜阶段就拦截，不是生成失败后才发现。
- **一致性靠"资产先行"**：角色三视图/主体库先固化为资产，所有镜头引用同一资产 ID（可灵主体库、Runway References 都是这个模式）。
- **双向修订**：台词先于画面写大概，画面出来后对着画面再改台词——规划物要支持回环，不是单向流水线。

### 2.3 剪辑器的技术收敛点（2026 年现状）

- **时间线即 JSON**：剪映 `draft_content.json`、Shotstack JSON Edit、OTIO——业界共识是 agent 操作的单位不是像素，是一份结构化时间线文档。agent 剪辑 = 对文档做 patch，等价于代码编辑器的 `replace_range`。
- **底座已切换**：ffmpeg.wasm 淘汰（纯 CPU、20-30MB、1080p/30s 要 30-60 秒）；WebCodecs 直通硬件编码（同任务 2-5 秒、浏览器支持率 95.5%）+ Mediabunny 封解封装。
- **最贴近的蓝图是 OpenCut 重写版**：Editor API（GUI 能做的一切都能 API 做）+ headless 渲染 + undo 栈对 agent 操作一视同仁 + **同一份文档两种视图**（人看 GUI，agent 看 JSON）。
- **Descript 粒度启示**：转写文本即时间线——"删掉这句口误" = 删掉对应片段，最高频剪辑操作从帧级降为文本级。台词轨必须是一等公民。

### 2.4 资产管理的铁律（DAM 行业共识）

- **引用而非复制**：时间线只存资产 ID + in/out 点，原始文件永不动。
- **版本号跨层同步**：时间线 v5 的导出必须叫 v5。
- **状态机与版本分离**：版本管迭代，状态（draft/review/approved/delivered）管流转，**杜绝 "final" 命名**。
- **血缘一等公民**：AI 生成资产必须自动记录 prompt/seed/模型/工作流版本（也是 EU AI Act / 加州 SB 942 的合规方向）；任一产物可回溯参数并 fork 重新生成。
- **命名规范由系统强制执行**（日期_项目_内容_序号_版本五段式）——agent 生成的文件天然遵守，这是 agent 相对人类团队的优势。

### 2.5 画布的定位（别做成又一个画图板）

调研结论：画布用于**混乱探索期**（moodboard、参考收集、结构未成形），内容收敛为线性交付物后就离开画布进文档。对 AI 视频，画布的真实价值是**节点化工作流复用**（角色卡 → 场景 → 分镜格 → 批量生成，连线一次搭好反复跑）和**点选式局部再生成**（Seko 模式：分镜是画布上的对象，单镜重抽不动其他）。

### 2.6 爆款工程（创作者方法论，2026-08-30 补研）

这一轮调研改变了 workflow 的形状，四个结构性发现：

- **封面前置是头部创作者的最大共识**：MrBeast 每条视频从标题+封面开始创意（它们设定预期，内容负责兑现）；Ali Abdaal 团队"没想好观众第一眼看到什么就不开工"；影视飓风把封面制作提前到选题会（AI 批量出 ~20 张封面参考，做不出好封面的选题直接不立项）。**包装不是发布前的收尾，是立项的准入门槛。**
- **脚本以留存检查点为骨架，不是线性文本**：钩子区（0-3s，抖音 80% 视频前 3 秒完播 <20% 直接淘汰，爆款 >70%）→ 兑现区（3-8s，钩子承诺立即兑现）→ 注意力单元序列（每 15-20s 一个"信息点+情绪点+转折点"，每 3-5s 一个视觉变化）→ 60% 处情绪峰值（峰终定律）→ 结尾转化窗口（一条视频只推一个动作，"理由在前动作在后"）。脚本用**秒针倒推法**写：先定 CTA → 倒推高潮点 → 倒推钩子。MrBeast 中长视频三检查点：30 秒 / 3 分钟（再参与点）/ 6 分钟（最高张力）。
- **复盘是数据驱动的固定动作，且回流生产端**：留存曲线四段归因（钩子区崩=承诺未兑现；中段塌=密度不足；结尾断崖=拖沓；全程平缓高=结构健康可复刻成模板）。发布后 checklist 有时间窗：0-3h 看冷启动（30 分钟内回前 20 条评论）、24h 四象限定性（CTR×留存）、72h-7d 留存对齐脚本节点、7-30d 沉淀选题库。跑出来的黄金 3 秒和爆款结构沉淀为**可复用模块库**——复盘成果固化回生产端，这是区别于"剪辑工具+表格"的闭环。
- **三平台算法权重根本不同**：抖音赌 3 秒留存（≈55% 及格线）+完播（≈38%）；B站赌深度互动（分享>投币>收藏>评论>弹幕>点赞，外显已改播放分钟数，中长视频结构性受益）；YouTube 赌 CTR×观看时长（知识类 CTR 5-8% 优秀，<2% 换包装；Test & Compare 官方 AB 测 3 标题×3 封面，按观看时长份额定胜负）。**同一选题的钩型、互动设计、时长按平台派生变体，不是一稿多投。**

知识区专项（与译宝定位最贴近）：逐字稿是全管线源数据（回形针一期 3-4 周，逐字稿占 1-2 周）；中文口播 220-260 字/分钟（时长校验基准）；misconception-first（先呈现观众的错误直觉再颠覆，Veritasium）；每个抽象概念在脚本阶段就要回答"它在屏幕上长什么样"（Kurzgesagt 视觉隐喻前置）；章节标题按 mini-headline 写法（独立命中搜索）；合集=追更引擎（B站订阅合集每次更新推送粉丝）。

## 3. 视频创作十幕（状态机）

```
[S0 选题]   选题库三层入口：随手积累（日常剪藏）/ 批量生成（agent 脑暴）/ 数据筛选（对标拆解）
            → 选题卡：HKRR 标注（快乐/知识/共鸣 ≥1 + 节奏可行）+ 钩型 + 目标平台
            → 封面前置（立门槛）：每选题 agent 产 3 版标题×封面概念，
              做不出好封面的选题直接淘汰（影视飓风/MrBeast/Ali Abdaal 共识）
            → 因果链可见：候选以 inline 卡落对话流，同时入库（选题库瓦片带"刚刚 +N · 来自本次对话"徽标）；
              点候选（流里/库里是同一对象）开选题 peek 比较 → 立项（L2）：创建项目实体 + 目录骨架。
              立项是相变，不是换张卡
  ▼ 人确认立项
[S1 脚本]   留存骨架写作（秒针倒推法）：先定 CTA（关注/评论/收藏/转发 四选一）
            → 倒推 60% 处情绪峰值 → 倒推钩子 → 顺填注意力单元（每 15-20s 一个）
            → agent 在编辑器器里出稿，锚定批注式修改（打 P2 的卡）
            → 静态校验：钩子区 ≤3s、价值承诺 ≤15s、口播 220-260 字/分钟折算时长、
              >5s 无信息点的冷区标红、结尾只推一个动作
            → 分平台变体：同一母稿派生抖音版（3s 钩子+密度）/B站版（三检查点+章节）/油管版（CTR+首分钟）
            → 脚本锁定 = 阶段门 ①（L2 人按印）
  ▼
[S2 分镜]   agent 拆分镜表：镜号(场-镜)/景别/运镜/画面描述/台词引用/时长/叙事目的/连续性
            → 每镜标注：它在屏幕上长什么样（视觉隐喻前置，Kurzgesagt）
            → 自动校验：单镜 3-8s（生成模型物理约束）、景别节奏、台词时长对轨
            → peek 成分镜表，人逐行改 → 分镜批准 = 阶段门 ②
  ▼
[S3 资产筹备] agent 从分镜提取主体清单（角色/场景/道具）
            → 画布上出三视图/场景参考图（多变体）→ 人钦定 → 入库（血缘完整）
            → 每镜绑定引用：主角=asset#c1、场景=asset#s2 ……（一致性靠资产先行）
  ▼
[S4 出镜头] 逐镜两阶段：首帧图（多变体并排，人钦定）→ 图生视频（批量队列）
            → 配额闸门：批量生成前报预算（N 镜 × 单价），L2 确认
            → 废片进回收站（可对比可复活）；失败 prompt 进复盘卡
            → 局部再生成：点选单镜重抽，其余不动（打"局部修改"断点）
  ▼
[S5 粗剪]   agent 按镜号自动拼装时间线 JSON：选定片段入轨 + 台词轨先行（TTS 或真人）
            → 按配音时长反调各镜画面长度
            → 粗剪预览 = 可播放的分镜表（"70 分初稿"）
  ▼
[S6 精剪]   时间线编辑器 stage：结构层 agent 做（粗剪/对齐/批量转场/字幕/去静音/响度），
            审美帧级人做（关键帧曲线/调色/卡点/转场手感）
            → 留存预检（机器可判的硬指标全部自动查）：每 3-5s 有视觉变化、
              无 >0.5s 无效停顿、结尾 BGM 渐弱保留 15%、结尾人像直视镜头
            → 时间码评论：「0:23 音乐换掉」→ agent 定位执行 → 人确认（打"agent 不理解工程"断点）
            → 画面锁定 = 阶段门 ③
  ▼
[S7 发布]   分平台打包：标题×封面 3×3 变体（对齐 YouTube Test & Compare 上限）、
            章节 mini-headline（B站看点/YouTube chapters）、标签（1 核心+3 长尾+2 场景）、
            发布时间（工作日 20:00-21:00）
            → 导出 = L3 人按印；发布后动作排进 reminders：
              30 分钟内回前 20 条评论、置顶讨论问题
  ▼
[S8 复盘]   守夜人按时间窗自动抓数据（0-3h 冷启动 → 24h 四象限定性 → 72h-7d 留存对齐）
            → 留存曲线四段归因：断崖在第几秒 → 改那一秒的画面和台词，一次只修一段
            → 四象限：CTR 低留存高=换包装；CTR 高前 3 秒崩=封面诈骗；双低=选题问题；双高=加码同类
            → 回流闭环：跑出来的黄金 3 秒/爆款结构沉淀进模块库，
              掉点+改法+下期验证项写回复盘卡，选题库按历史分组表现重新排序
            → 散场：资产归档、任务轨迹入地平线、版本号封存 DELIVERED
```

校验规则沿用总纲：**每一幕说不出对应事件/tool 的元素就是装饰，删。**

## 4. 数据模型：资产引用血缘图

项目实体的第一个真实用例（`2026-08-30-project-entity-design.md` 的落地检验）。引用式挂载，不搬数据：

```
project:video {
  id, name, dir                        // 目录骨架自动创建（见 §8.1）
  objects: [
    { type: "video.script",   ref }    // 剧本（版本栈 + 状态机）
    { type: "video.storyboard", ref }  // 分镜表（镜头卡片集合）
    { type: "video.canvas",   ref }    // 画布（探索期）
    { type: "video.timeline", ref }    // 时间线 JSON
    { type: "video.asset",    ref } ×N // 素材（角色/场景/镜头/音频/导出）
  ]
}

shot（镜头卡片 = 一等对象，分镜表的行）{
  id: "S02-E03"                        // 场-镜
  scene, shot_size, camera_move,       // 景别/运镜（枚举，校验用）
  description,                         // 画面描述（出图 prompt 的原料）
  dialogue_ref,                        // 台词引用 → 剧本行（双向同步）
  duration_est,                        // 台词推导的时长
  narrative_purpose,                   // 为什么有这镜（最容易丢的字段，必须有）
  refs: { character: [asset_id], scene: asset_id },   // 一致性引用
  frames: [asset_id ×N 变体], selected_frame,          // 首帧版本族
  clips:  [asset_id ×N 变体], selected_clip,           // 视频版本族
  status: draft → framed → clipped → locked
}

asset {
  id, kind: image|video|audio|text,
  file,                                // 文件名系统强制五段式命名
  lineage: { prompt, seed, model, params, parent_asset? },  // 血缘
  status: draft → review → approved → delivered,       // 状态机 ≠ 版本
  referenced_by: [shot_id | timeline_id]               // 引用计数（删前警告）
}

timeline {                             // 单一事实源：人看 GUI，agent 看 JSON
  version: v{n},                       // 与导出强制同步
  tracks: [ { clips: [{ asset_ref, in, out, speed, effects, keyframes }] } ],
}
```

三条铁律执行点：引用而非复制（timeline 只存 asset_ref + in/out）；版本跨层同步（导出物版本号 = 时间线版本号）；状态机与版本分离（杜绝 final）。

## 5. 器的清单与提升决策

按总纲标准（被 ≥2 个任务域需要的重交互组件才提升进宿主）：

| 器 | 状态 | 决策 |
|---|---|---|
| **编辑器**（文本） | zimeiti 私有，agent 通道已通 | **提升**——剧本（视频）和稿件（zimeiti）两个域都需要。P2 锚定批注的载体，video case 是它的第二个真实用户 |
| **分镜表**（storyboard） | 不存在 | **新建并提升**——结构化镜头卡片（不是画布上的自由图片）。视频/短剧/漫画分镜通用。本质：带 schema 的表格器 + 每行展开成卡 |
| **画布**（canvas） | 不存在 | **新建**——探索期专用：moodboard、三视图、首帧多变体。分镜格是它的对象不是它的全部。收敛后让位 |
| **时间线编辑器**（timeline） | 不存在 | **新建并提升**——本 case 最重的器。双视图：GUI（人）+ JSON（agent）。底座见 §8.2 |
| **选题库**（topic pool） | zimeiti 有选题，无视频语义 | **复用扩展**——三层入口（随手积累/批量生成/数据筛选）+ 每条选题挂标题封面候选 + HKRR 标注 + 历史表现回写 |
| **留存分析**（复盘面板） | zimeiti 有 stat 雏形 | **扩展**——留存曲线 + 四段归因 + 发布后排程 checklist（接 reminders）+ 数据回写选题库 |
| **diff 卡** | 通用原语 | 复用——所有 agent 写操作（改剧本/改台词/时间线 patch）的确认载体 |
| **看板/素材轨** | zimeiti 有 | 复用——素材库就是带血缘的看板 |

关键架构含义：**视频创作不写新页面**——立意到交付全流程 = 对话（基底）+ 五个器在四种呈现密度（inline/peek/stage/focus）上的聚散，聚散规则见 §6。这是检验清单第 1 条的实战验证。

## 6. 位的模型：三种主导模式 × 四种呈现密度

> 2026-08-31 修订。旧稿把 inline/peek/stage/focus 并列成"四种位"，走查讨论发现这混淆了两个层级。修正为 3+1 模型：**工作台有三种主导模式；任何器/对象有四种呈现密度**。peek 不是第四位，是唯一不占现场的密度档。

### 6.1 三种主导模式（工作台的态）

沿主导权梯度排布。**决定权沿轴不移动**——阶段门永远在人手里（§3 的四道门）；沿轴变化的是发起权和劳动占比。

| 模式 | 发起权 | 劳动分配 | 人的动作 | 对话密度 |
|---|---|---|---|---|
| **对话**（家态基底） | agent 发起多（建议/守望/提问） | agent 干（出候选/出稿） | 动嘴：聊方向、定去留 | 完整流 |
| **stage**（生产现场） | 共同发起 | agent 做粗活、人做判断 | 锚定批注、裁决 diff | 驻底细条 + 批注栏 |
| **focus**（裁决现场） | 人发起（双击那一下） | 人做决定；agent 压缩成器械（"再来一版"背后是整条生成管线） | 留 / 杀 / 再来 | 只剩裁决钮 |

focus 里 agent 不是降级成助手，是压缩成器械。

### 6.2 四种呈现密度（器/对象的态）

| 密度 | 形态 | 占现场？ | 用途 |
|---|---|---|---|
| inline 卡 | 嵌在对话流里 | 占对话 | 流内交付物（候选卡、闸门卡） |
| **peek** | 浮层预览，Esc 即走 | **不占** | 瞬态查看 |
| stage | 铺满桌面：器中 + 批注栏 + 溪流导航 | 占满 | 协作生产 |
| focus | 独占全屏，其余沉入地平线 | 独占 | 单对象裁决 |

### 6.3 peek 的正名（为什么不鸡肋）

peek 不住在主导权轴上，它是**器的预览态 + agent 主动性的承载层**。两条不可替代的职责：

1. **现场保护**：stage/focus 中所有"5 秒钟的问题"（提醒到了、曲线出了、候选好了），没有 peek 只有两条路——切走（丢现场）或积压（丢感知）。
2. **agent 主动性的礼貌出口**：守夜人场景（留存曲线出了、队列跑完了、蹲到热点了）发生时人通常不在对话里。agent 主动找人只有三个选项——霸占 stage（粗鲁）、写进 chat 等人回来（延迟且仍要切现场）、peek 浮层轻拍肩膀（看完 Esc 即走）。**没有 peek，agent 的主动性要么烦人，要么隐形。**

设计纪律：**peek 里只允许"看 + 一个决定"**。决定也分轻重：轻决定（意图登记如「立项」、导航如「修这段」、「知道了」）在 peek 里完成；**L2/L3 按印永远回落到对话流里的闸门卡**——闸门是一个正式对话回合（agent 汇报 → 人按印 → 可否决），要有记录、在地平线留痕，不配发生在瞬态浮层里。需要第二个动作就必须升格 stage。这条纪律防止 peek 膨胀成鸡肋的中间态。

### 6.4 承接：位之间流动的是对象，不是消息

- peek → stage：带对象。peek 里"打开"，stage 直接落在该对象的工程现场。
- stage → focus：带选中。双击一镜，focus 审这一镜。
- focus → stage：带决定。杀/留/批注**写回对象本身**（时间码评论、回收站），回到 stage 现场已更新。
- stage → 家态：过阶段门，项目卡进到下一阶段。
- **继续一个项目 = 状态恢复，不是翻聊天记录**：项目卡显示当前阶段 + 下一步动作 + 待你定数量，点开即恢复现场（打开的器、待批的 diff、队列状态）。三条入口：家态项目卡 / 对话路由（"继续做品牌短片的分镜"）/ 底栏常驻空间入口。

对话不是第四种位，是贯穿三种模式的伴生层，密度随位变。**表面跟随选择：人选中了什么，agent 的注意力就在什么上**——不需要重新向 agent 描述上下文。

### 6.5 一个完整流转的例子（译宝品牌短片 60s）

```
家态(inline 聊) ─点卡→ peek(瞥) ─立项→ 项目卡 ─打开→ stage(做)
                                    ↑              │双击对象
                            阶段门通过│              ▼
                            带决定回来│            focus(定)
                                    └──────────────┘
提醒 ─点→ peek(瞥) ─"修这段"→ stage(做)        ←── 对象全程携带
```

1. **inline → peek（选题）**：对话里出 3 个候选（inline 卡，同时落选题库）→ 点卡开 peek：封面概念×3 + HKRR + 同类完播。瞥十秒，Esc 即走，或点「立项」。立项 = 选题卡**相变**为项目实体，不是换张卡。
2. **家态 → stage（写脚本）**：点项目卡进 S1。译宝初稿以 diff 卡进批注栏；你选中钩子句，输入框钉在锚点上："这个钩子太平。"选中即指令，指令和目标是一个动作。
3. **stage → focus（审一镜）**：分镜表里双击 E03 → 满屏只剩这一镜和 留/杀/再来。
4. **focus → stage（带决定回来）**：点「再来一版」。回到分镜表，E03 已是新版——决定写回了对象，不是写在聊天记录里。
5. **stage → 家态 → peek（复盘）**：发布三天后提醒瓦片亮起 → peek 看留存曲线：0:42 掉点，归因"中段塌 = 密度不足"。
6. **peek → stage（修 0:42）**：点「修这一段」→ S6 时间线打开时那段已被选中。修复归因由守夜人回写选题库——对象流了一圈，变成下一个选题的养分。

## 7. 人机分工矩阵

| 环节 | agent 做 | 人做 | 断点对策 |
|---|---|---|---|
| 选题 | 批量脑暴、对标拆解、HKRR/封面前置过滤 | 拍板"做什么" | 做不出好封面的选题直接淘汰 |
| 脚本 | 初稿（秒针倒推）、留存骨架校验、改写提案（diff 卡）、分平台变体 | 审校、锚定批注、CTA 裁决 | 人和 agent 同一编辑入口 |
| 分镜 | 拆镜、字段填充、时长/节奏校验 | 逐行改、叙事目的裁决 | 分镜表 = 共同界面（MovieAgent 模式） |
| 资产 | 主体清单提取、三视图生成、血缘记录 | 钦定版本 | 多变体并排 + 钦定制 |
| 出镜头 | 批量队列、失败重试、复盘统计 | 选片、判废 | 配额闸门 + 回收站 |
| 粗剪 | 全做（拼装/配音对轨/字幕） | 看片提意见 | 时间码评论 → agent 定位执行 |
| 精剪 | 结构层（去静音/批量转场/响度/对齐）、留存预检 | 审美帧级（曲线/调色/卡点） | agent 操作全进 undo 栈、可见可撤销（Descript 教训） |
| 发布 | 分平台变体打包、章节/标签/发布时间、checklist | 按印（L3） | 发布后动作排进 reminders |
| 复盘 | 定时抓数据、四段归因、四象限定性、写复盘卡 | 看结论、定下期方向 | 回流闭环：模块库 + 选题库重排 |

核心原则（Rule of Six 的产品化）：**情感>故事>节奏>视线>轴线>空间**——剪辑点决策的权重体系决定 agent 只能给候选和建议，采纳键在人手里。

## 8. 技术架构

### 8.1 目录骨架（立项时 agent 自动创建，命名强制）

```
{project}/
  01_素材/    # 角色/场景/镜头片段/音频（血缘元数据 sidecar）
  02_工程/  # timeline JSON、分镜表、剧本
  03_导出/    # 版本号与时间线同步，DELIVERED 状态后缀
  04_文档/  # 创意卡、复盘
```

### 8.2 时间线双引擎

- **预览/快速迭代**：WebCodecs + Mediabunny 本地即时渲染（硬件编码，2-5 秒级）
- **终出片**：FFmpeg 做编译目标（上层维护时间线 JSON，FFmpeg 只渲染）或 headless 渲染管线
- **出口**：OTIO（进专业 NLE）+ 剪映草稿 JSON（pyJianYingDraft 生态，务实退路——"AI 出草稿、人在剪映精修"今天就能跑通）

### 8.3 agent 的编辑原语（五层，与 editor.* 同构）

```
读：timeline.get / getClips / getTranscript / detectSilence
结构写：addClip / trim / split / move / delete / addTransition（全部 = 对 JSON 的 patch）
参数写：setSpeed / setVolume / applyEffect / addCaptions(SRT 批量)
关键帧：setKeyframe（agent 生成初值，人调曲线）
渲染：export(settings) + 进度回调
```

机制不变量（复用裁决器）：

- **undo 栈对 agent 一视同仁**：agent 的每个 patch 是独立可回退单元，人在 GUI 里一键撤销（Descript 教训的正面解）
- **写操作过确认**：批量 patch 先出 diff 预览（时间线前后的结构对比），人放行才落
- **配额闸门**：生成类调用（出图/出视频）默认 L2，批量执行前报预算；导出 L3
- **同一份文档**：GUI 时间线和 agent 看到的 JSON 是同一对象，不存在"agent 看不见的自定义"（Descript 断点的根因解）

### 8.4 台词轨一等公民（Descript 模式）

转写文本即时间线的入口：删一句台词 = 删对应片段；配音时长反推镜头时长；字幕从台词轨派生。这同时是 S5 粗剪自动化的数据基础。

## 9. 打磨清单：这个 case 要压过的机制检查点

每一格对应总纲检验清单，做完才算"顺畅"：

- [ ] **不写新页面装配出工作台**：视频创作全流程只靠对话 + 五个器在四种呈现密度上聚散
- [ ] **agent 不靠截图读写**：剧本（editor.read）、分镜表（storyboard.get）、时间线（timeline.get）、素材（asset.list）全部结构化可达
- [ ] **编辑器全库一份**：zimeiti 和视频剧本共用同一编辑器器（倒逼提升）
- [ ] **人机同一入口**：改剧本 / 钦定版本 / 接受时间线 patch——人点和 agent 调收敛到同一事件流
- [ ] **生命周期聚散**：S0 立项 → S8 散场，项目/器/资产随阶段门进出，地平线全程记账
- [ ] **出生证**：每个镜头片段可从时间线回溯到分镜镜号 → 首帧 → prompt/seed → 产生它的那条对话
- [ ] **配额经济学**：批量生成前报预算，废片有回收站，失败有复盘
- [ ] **项目实体落地**：引用式挂载、ctx 读数、跨域聚合在这个 case 第一次跑真
- [ ] **复盘回流闭环**：发布后时间窗 checklist 自动排程（reminders）、留存曲线四段归因、掉点回写选题库、黄金 3 秒沉淀进模块库——爆款方法论复利，不是一次性感想
- [ ] **stage 三协作通道**：锚定批注（选中即指令）/ 驻底指令条（无锚指令）/ agent 主动提案（diff 卡待裁决）都通
- [ ] **peek 纪律**：预览 = 看 + 一个决定；需要第二个动作自动升格 stage
- [ ] **继续 = 状态恢复**：项目卡点开恢复上次现场（打开的器、待批的 diff、队列状态），不靠翻聊天记录

## 10. 分期实施

- **V0 · 纸面走查**（本文档 + 原型小样）：十幕状态机的静态 HTML 走查稿，无生成功能——先验证"聚散"的手感。**已完成**：`specimen/video-flow.html`（13 幕：总览 + S0–S8 + focus 审片 + 小窗陪伴）
- **V1 · 规划段**（S0–S2）：项目实体 + 目录骨架 + 编辑器提升 + 选题库（封面前置）+ 分镜表器。依赖：P2 锚定批注（剧本修改体验的地基）
- **V2 · 生成段**（S3–S4）：画布器 + 素材库（血缘/版本族）+ 批量生成队列 + 配额闸门。依赖：图像/视频生成的 tool 接入（skill 层）
- **V3 · 剪辑段**（S5–S7）：时间线器（WebCodecs 底座）+ 编辑原语 + 台词轨 + 分平台导出
- **V4 · 复盘段**（S8）：留存分析面板 + 发布时间窗 checklist（reminders）+ 模块库回流
- 每期结束用同一个真实片子（比如一支 60 秒的产品短片）走全程验收，卡哪补哪

## 11. 开放问题

1. **生成后端**：自建 skill 调各家 API（可灵/即梦/Runway）还是只接一家？多模型混合管线（一致性用一家、批量用一家）是行业常态，但接入成本高——V2 再定
2. **画布底座**：自研还是 tldraw SDK（商用 $6000/年）？探索期画布和分镜表的关系还要在 V0 原型里试
3. **时间线底座**：OpenCut 重写版（MCP/Editor API，2026-08 仍在开发中）vs Diffusion Studio core vs 自研薄层——V3 立项时评估，别现在赌
4. **台词轨与画面轨的同步语义**：改台词 → 该镜时长变化 → 后续镜头 ripple？规则要细想
5. **TTS 配音**进不进 scope？（S5 粗剪"按配音时长反调画面"依赖它，但本身是个大能力）
6. **项目实体与 zimeiti 选题的关系**：视频项目可能就是从选题长出来的——挂载还是派生？
7. **peek 与通知体系的分工**：提醒瓦片 / peek 浮层 / 系统通知三者边界——什么级别的 agent 主动行为配用 peek 抢占注意力？
8. **focus 的进出手势**：双击 / 快捷键 / Esc 的具体交互，以及 focus 内"再来一版"的参数化程度（口头说一句 vs 调出参数面板）——V0 原型里试

## 附：调研关键数字速查

- 抽卡成本：单镜头 45–300 元；项目成功率实测 30–60%（官方口径 90%+ 是营销）
- 台词时长：2.5–3 词/秒（英文）；中文口播 220–260 字/分钟
- 单镜头时长：3–8 秒（生成模型物理约束）
- 资产版本：视频项目 10–30+ 修订循环是常态
- WebCodecs vs ffmpeg.wasm：1080p/30s 编码 2-5 秒 vs 30-60 秒
- 素材混乱的代价：每天找素材浪费 50–100 分钟（DockBuddy 统计）
- 脚本时间占比：单人创作者一条视频 ~5.5h，脚本占 45–60%
- 留存基准：抖音 3 秒留存 ≈55% 及格/爆款 >70%；5–10 分钟视频平均留存 31.5%（最优时长区间）；教育科普类 42.1%（品类最高）；YouTube 知识类 CTR 5–8% 优秀、<2% 换包装
- 注意力密度：每 3–5s 一个视觉变化；每 15–20s 一个「信息点+情绪点+转折点」；情绪峰值放 60% 处（峰终定律）
- B站权重：分享>投币>收藏>评论>弹幕>点赞；发布后 7 天为关键期、当天评论占比 ~49.5%
- 封面前置：缩略图驱动 90% 点击决策；用户点击决策窗口 0.3–3 秒
- 真人 vs AI 配音：人声留存率高 ~35%
